TU/e Research Data Support

Assess and Prepare Research Data for Reuse and Repository Deposit

The FAIR Data Clinic assesses the files, documentation, metadata, provenance, software, rights, and other evidence that make up a research data package before repository deposit. It identifies reuse barriers, supports correction and reassessment, and then prepares the case for Data Steward review and repository deposit.

Why test material is required: file contents are processed locally, but this proof of concept is not an approved secure service. Browser storage is not encrypted, case metadata and findings may remain on the workstation, and the application has not completed institutional privacy, security, or production-deployment approval. Use fictitious contact details and non-sensitive or explicitly approved files.
Why there is a Data Steward workspace in RC15: researchers can correct routine preparation issues themselves and can record that they need help on individual findings, while the current 5.8 workflow still requires Data Steward review before repository-preparation readiness is confirmed. The Data Steward interprets evidence, resolves professional findings, routes privacy, ethics, legal, security, and repository questions, and records the preparation outcome. Selecting this workspace does not authenticate the user or confer institutional authority.

About the FAIR Data Clinic Toolkit

Purpose, proof-of-concept boundaries, and current limitations.

About this toolkit

The FAIR Data Clinic Toolkit is a standalone proof of concept for pre-deposit Dataset Content and Reuse Readiness assessment within a combined researcher and Data Steward workflow. Its primary function is to inspect and evaluate the files, documentation, metadata, provenance, software, rights, access information, and relationships that constitute a research data package while those elements can still be corrected before repository deposit.

Researchers can resolve routine preparation findings themselves, record clarification, reassess corrected files, and indicate when they need help. In the current 5.8 architecture, Data Stewards still review the submitted evidence, reconcile professional findings, route specialist issues, request changes where required, and retain final authority over repository-preparation readiness. The planned v5.9 redesign of conditional self-service versus mandatory professional escalation is deliberately not implemented in RC15.

The toolkit uses the established 12-criterion Dataset Content and Reuse Readiness assessment model. It does not calculate or certify a FAIR score. 4TU.ResearchData is the first repository-specific preparation profile, but repository-specific preparation is downstream of the package assessment and RC15 has no live repository connection. The toolkit generates a Schema.org Dataset JSON-LD representation from public preparation metadata. The internal case structure is prepared for later RO-Crate mapping, but this release does not generate or claim conformance to a full RO-Crate.

README guidance provenance: The generated README structure and deterministic README checks are informed by the EPFL RDM Team README best-practices guide and template (2022), which cites the 4TU.ResearchData Guidelines for creating a README file (July 2020). These sources inform preparation guidance; they do not create repository acceptance or institutional approval.

README Documentation Completeness: The toolkit operationalizes applicable README guidance into two transparent coverage measures: core completeness for strongly recommended elements and overall documentation coverage for core plus supporting elements. No arbitrary point weighting is used. Not-applicable and not-assessed elements are excluded from the denominator, and conflicts remain visible separately.

Assessment prior art: The toolkit credits the CABI FAIR Process Framework Data Self-Assessment Tool for selected dataset-maturity, metadata-persistence, semantic-vocabulary, personal-data/licensing, and decomposed-provenance concepts. The Clinic independently implements evidence-based pre-deposit preparation controls and does not adopt CABI’s agricultural FAIR scoring model.
Lineage: CABI credits the DANS SATIFYD tool (2019). DANS identifies FAIR-Aware as the supported successor to SATIFYD. The ARDC FAIR Data Self-Assessment Tool is recorded as related educational prior art. These sources inform positioning, educational progress presentation, and rule concepts; none confers institutional authority or repository acceptance.
RC15 stabilization boundary: this release improves clarity, usability, accessibility, and release verification within the existing 5.8 architecture. The new reuse-readiness engine architecture, canonical evidence model, conditional Data Steward routing, and live 4TU, Zenodo, and Dataverse adapters belong to v5.9 and later.

Built and maintained by Richard Dennis. UI design assisted by AI (Claude).

How the POC works

Files are selected and analyzed locally in the browser. The assessment produces evidence signals and preparation actions; researchers can correct routine issues and reassess the package before submitting the case for the current Data Steward review stage. Shared work is simulated by exporting and importing a structured JSON case handoff. The handoff contains case information, findings, comments, decisions, status, and audit history; it does not create a shared institutional workspace.

Local processing is not the same as an approved secure environment. Browser case storage is not encrypted, names and email addresses are personal data, and manifests, checksums, findings, comments, and entered metadata may remain on the workstation. Use fictitious contacts and non-sensitive or explicitly approved files. Delete cases through Manage all cases and clear the browser site data when the local test record is no longer required.

Repository preparation in RC15 is simulated locally. No metadata or files are transmitted to 4TU.ResearchData, Zenodo, Dataverse, JSM, Research Cockpit, or RAPS. A future institutional implementation would require authentication, approved storage, role-based permissions, retention rules, records-management decisions, secure repository credentials, and formal security, privacy, accessibility, and service-owner review.

Known limitations

  • No authentication or real multi-user access.
  • No server-side storage, notifications, or real-time collaboration.
  • Selected file contents are not retained after the browser session.
  • Export/import simulates handoff and can create version-management risk if users exchange the wrong revision.
  • Technical findings and assessment signals remain pre-deposit evidence, not a FAIR certification, scientific-quality determination, legal decision, or repository-acceptance decision.
  • The README Documentation Completeness percentage measures applicable documentation coverage only. It is not a dataset reusability score or readiness percentage.
  • The current 5.8 workflow still requires Data Steward review before repository-preparation readiness is confirmed. Conditional self-service escalation is a v5.9 architectural change, not an RC15 feature.
  • The 4TU preparation panel is not connected to 4TU.ResearchData. RC15 does not create repository drafts, upload files, reserve DOIs through an API, or synchronize repository metadata.
  • No live JSM, Research Cockpit, RAPS, Zenodo, Dataverse, or other repository integration.
